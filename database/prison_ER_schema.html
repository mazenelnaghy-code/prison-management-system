5. Reduction Rules Applied (mapping ER → Relational, per Ch 7_3)

  1. Strong entity sets → one table each. Cell, Crime, Kitchen, Staff, Guards, Prisoners, Visitors, BackupForces, Emergencies, Users are all strong — each becomes a relation with the same attributes and the same primary key. (Ch 7_3 — "Strong Entity-Sets with simple attributes")
  2. 1 : N relationships → foreign key on the "many" side. No separate table is needed for the relationship; instead, the primary key of the "one" side is added as a foreign key column to the "many" side. Applied to:
    • Employs → RestaurantID added to Staff
    • Patrols → CellID added to Guards
    • Houses → CellID added to Prisoners
    • Site_of → CellID added to Emergencies (nullable because participation is partial)
  3. M : N relationships → new junction table. The relationship becomes its own relation whose attributes are the union of the participating entities' primary keys plus any descriptive attributes of the relationship. Applied to:
    • Committed → PrisonerCrime(PrisonerID, CrimeID, CrimeDate)
    • Visited_by → Visits(PrisonerID, VisitorID, VisitDate)
    • Responds_with → EmergencyBackup(EmergencyID, BackupID)
    A surrogate PK (PrisonerCrimeID etc.) is used in the built database for convenience; the natural composite PK of the relationship would otherwise be the union of the two foreign keys.
  4. 1 : 1 relationships → foreign key on either side (chosen by participation). The Has_account relationships between Users and (Staff / Guards) become two nullable foreign keys (StaffID, GuardID) on the Users side, because participation on the Staff/Guards side is partial (not every staff member has a login). (Ch 7_3 — "Schema Combination — One-to-one")
  5. Descriptive attributes of a relationship. CrimeDate on Committed and VisitDate on Visited_by are stored as columns of the corresponding junction tables, exactly as the textbook prescribes for an attribute hanging off a diamond. (Ch 7_3 — "Relationship-Set Example: borrower")
  6. Domain constraints → CHECK / validation rules. Crime.SeverityLevel ∈ {Low, Medium, High, Critical} and Users.Role ∈ {Admin, Staff, Guard} are implemented as validation rules in the resulting database. (Ch 7_1 — "Constraints")
  7. Referential integrity. Every foreign key is declared with referential integrity enforced + cascade update, matching the constraint type defined in the ER model. (Ch 7_1 — "Keys")
  8. No weak entity sets in this schema. Every entity is independently identifiable by its own surrogate ID, so the weak-entity rules from Ch 7_1 (dashed-underline discriminator, double-diamond identifying relationship, composite PK = owner PK ∪ discriminator) are not applied here. They would apply if, for example, Visit had no surrogate VisitID and were identified only by (PrisonerID, VisitorID, VisitDate).
